# 教学仿真资源管理模块（`resource_management`）

本文件是模块的**接口与数据契约**，与 `docs/data_contract.md`（工程一致性验收）
配套。只描述代码里实际存在的行为。

定位：**独立的教学沙盒**。不接真实设备控制接口。

* **实验入口完全不引用本模块**——产生实验数字的脚本（`main.py`、`train_dqn.py`、
  `evaluate_*.py`、`sensitivity_energy_budget.py` 等）里**一个字都不出现**，
  因此"新增本模块没有改变历史实验行为"是可证明的，而不是靠声明。
* **验收脚本可以只读引用**：`verify_v4.py` §15 的一致性校验会导入本模块，
  但不驱动它产生任何实验数据（由
  `tests/test_resource_management.py::TestNoHistoricalEntryPointCoupling` 钉住）。

本阶段交付：**多节点资源模型 + 统一执行器**。

---

## 1. 资源单位（必须显式）

"节点用了 3 个资源"在工程上没有意义，除非说清 3 个**什么**。
所有单位定义在 `units.py`，每个都带中文名与"一个单位代表什么"：

| 单位 | 中文名 | 符号 | 一个单位 = |
| --- | --- | --- | --- |
| `sample_slot` | 采样时隙 | `slot` | 一次驻留观测（对场景扫一遍） |
| `processing_op` | 处理配额 | `op` | 一次关联 + 一次滤波更新 |
| `comm_byte` | 通信字节 | `B` | 一字节共享载荷 |
| `occupancy_second` | 占用秒 | `s` | 节点被该任务独占 1 秒 |

前三个是**预算**（会被消耗/预留）；`occupancy_second` 是**时间占用**，
记成占用区间而不消耗预算。**必须分开**，否则"节点忙但资源充足"与
"节点闲但资源耗尽"这两种完全不同的故障会被混成一种。

### 1.1 教学成本模型与真实装备无关

`TEACHING_COST_MODEL` 里的数字是**为了把多节点资源竞争演示清楚**而人为设定的：

| 任务 | 采样时隙 | 处理配额 | 通信字节 |
| --- | --- | --- | --- |
| 采样 | 1 | 1 | 0 |
| 处理 | 0 | 1 | 0 |
| 共享 | 0 | 0 | 128 |
| 空闲 | 0 | 0 | 0 |

⚠️ 单位之间没有换算关系，也没有标定过任何真实雷达。
**不得**用它们推断真实装备的采样能力、处理吞吐或通信带宽。
要让成本更接近现实，正确做法是在配置里替换成实测标定值。

## 2. 五个统一数据结构

| 结构 | 位置 | 作用 |
| --- | --- | --- |
| `NodeState` | `model.py` | 一个节点的可用性、更新周期、占用区间、预算、历史估计、统计 |
| `ResourceBudget` | `model.py` | 三类预算的 `capacity` / `consumed` / `reserved` |
| `TaskRequest` | `model.py` | 单个任务：节点、类型、开始时刻、时长、成本、去重键、涉及对象 |
| `ExecutionPlan` | `model.py` | **一份计划同时描述多个节点**的采样/处理/共享/空闲任务 |
| `ExecutionResult` | `model.py` | 计划状态 + 逐任务结果 + 校验问题 + 账本条目 ID |

辅助结构：`ValidationIssue`（`scope` 决定处置范围）、`TaskOutcome`
（`outcome` + `reason_code` + `reason`）、`LedgerEntry`、`Estimate`
（带 `age_of(now)`）。

### 2.1 `ResourceBudget` 为什么有 `reserved`

任务有**占用区间**。`start_s == now` 的任务立即消耗；`start_s > now` 的任务
先把成本**预留**下来，否则同一份预算会被两个未来任务重复承诺。
时钟推进到 `start_s` 时预留转为消耗（账本记一条 `activate`）。

**守恒不变量**（每个预算单位）：

```
capacity == consumed + reserved + remaining    且三者均非负
```

`conservation_residual()` 给出逐单位残差，`conservation_report()` 逐节点汇总。

## 3. 唯一全局时钟

`GlobalClock` 是**唯一**的 `now` 来源：

* 执行器只**读取** `clock.now_s`，从不自己算时间；
* 推进只通过 `advance_to(t)` / `advance(dt)`，**每个 tick 只调用一次**；
* `step_count` 记录推进次数——测试用它证明
  "N 个节点、M 个任务只推进一次"；
* `history` 记录 `(from, to, reason)` 便于追溯；
* **只允许向前**：时间倒流直接抛 `ClockError`（信息年龄与占用区间都依赖单调时间）。

执行器**不持有任何世界实体**。唯一允许在推进时产生副作用的通道是
`clock.subscribe(hook)`，执行器用它把到期预留转为消耗；
该回调拿不到目标、通信队列或其他实体，因此不可能出现
"顺手再推一次"的写法。这一条由 `test_executor_does_not_touch_other_world_entities`
用探针世界钉住。

## 4. 提交契约：两阶段 + 两类失败

```
submit(plan)
  ├─ 阶段 1  全量校验（只读，绝不改状态）
  └─ 阶段 2  执行与记账（仅在**没有计划级致命问题**时进入）
```

### 4.1 两类失败的处置**必须分清**

| 类别 | 触发条件 | 处置 |
| --- | --- | --- |
| **计划级致命** `PLAN_FATAL` | 未知节点、未知任务类型、负成本/负时长、`start_s` 与当前时钟不符、计划内 `task_id` 重复、去重键已执行过、占用区间冲突 | **整份计划不执行**：一个单位都不扣，状态快照**逐位不变** |
| **节点局部** `NODE_LOCAL` | 该节点不可用、该节点资源不足、采样更新周期未到 | **只拒该节点的任务**，其余节点照常执行；**不得**因此结束整个网络任务 |

把两者混成一种，就会出现"因为 C 节点没配额，A/B 节点的采样也一起没了"——
这正是要禁止的行为。

### 4.2 本版本的执行语义（边界）

* **只支持立即执行**：`start_s` 必须等于当前时钟。
  未来任务（`start_s > now`）会被判为 `illegal_start_time`。
  这样做的原因是避免在第一次交付里就引入调度器语义；
  预留机制（`reserved`）已经就位，接入调度器时不需要改数据结构。
* **一个节点在同一时刻只能有一个任务**：占用区间重叠即冲突。
  空闲任务时长为 0、不占区间，因此空闲可以与别的任务共存。
* **更新的周期约束只作用于采样**：两次采样之间至少间隔 `update_period_s`。

---

## 5. 空闲语义

* 零成本、零占用区间；
* **不产生任何采样报告**（`produced_samples == 0`，账本条目显式说明）；
* 历史估计**保留**，但其**信息年龄**随全局时钟增加
  （`Estimate.age_of(now)` / `NodeState.max_information_age_s(now)`）；
* 账本条目记下当时的 `information_age_s`，便于追溯"空闲期间信息旧了多少"；
* 采样会把对应实体的信息年龄**刷新回 0**。

实测（`tests/test_resource_management.py`）：采样后年龄 0.0 s，
空闲 3 s 后年龄 3.0 s；NODE_B 在 t=13 采样而 NODE_A 最后一次采样在 t=9，
于是同一时刻两者的年龄分别是 0.0 s 与 4.0 s。

## 6. 账本：三个问题的一次过滤

验收要求是"两个节点分别在做什么、用了多少资源、为什么某项任务没有执行，
都能**从账本追溯**"。因此账本是结构化记录而非日志，每条带
`node_id / task_id / plan_id / kind / 时间 / 逐单位增量 / 记账后余额 / 原因`：

| 问题 | 查询方式 |
| --- | --- |
| 某节点在做什么 | `ledger.of_node(node_id)` 里 `consume` 条目的 `kind` 与节点占用区间 |
| 用了多少资源 | `ledger.totals_by_node()` 逐单位汇总（与 `budget.consumed` 一致） |
| 为什么没执行 | `ledger.rejections(node_id)` 的 `reason_code` + `reason`（含具体缺口） |

账本**只记录，不判定**：所有"能不能执行"的判断都在执行器里，
账本不参与决策——否则审计材料会与决策逻辑互相污染。

条目类型：`consume` / `reserve` / `activate` / `release` / `reject` / `idle`。

## 7. 产物（复用运行隔离契约）

`python -m resource_management` 与 `resource_management.reporting.write_artifacts()`
把结果写到 `output/runs/<run_id>/resource_management/`：

| 文件 | 内容 |
| --- | --- |
| `ledger.csv` | 逐条账本 |
| `ledger_by_node.csv` | 逐节点汇总（容量/消耗/预留/剩余/守恒标志/拒绝次数/信息年龄） |
| `execution_log.csv` | 逐计划执行日志（状态、执行/拒绝数、涉及节点） |
| `nodes.json` | 各节点最终状态 + 守恒报告 |
| `manifest.json` | `run_id` / `config_digest` / `source_digest` / 产物清单（含 sha256） |

`RunManifest` 带 `tool` 字段，因此 `latest_run_dir(root, tool=...)` 能按工具
过滤——**不同工具各自写运行目录时不互相覆盖，取"最新"也不会取错工具的那次**
（这一点实测踩过：`verify_v4` 一度取到资源管理那次运行，导致找不到压力测试产物）。

## 9. 本阶段**没有**做的（下一阶段闸门）

* **没有接真实设备控制接口**（本模块不产生任何对外控制指令）；
* **没有调度器**：只支持立即执行；`reserved` 机制已就位但尚未被调度器使用；
* **没有节点间依赖/任务队列**：任务之间的先后约束尚未建模；
* **没有与仿真真值、传感器测量的耦合**：本模块的"采样报告"是抽象产物，
  尚未与 `sensor/` 的 `MeasurementRecord` 对接（对接必须在信息边界
  §3.2 的约束下做）；
* **没有性能目标**：验收标准是执行顺序、时间推进与资源守恒的一致性，
  **不是**性能提升。

## 10. 融合结果 → 资源调度适配层（v4.5）

### 10.1 要修的断点（核对记录 E2）

"融合器输出存在" ≠ "调度器已经真正使用了它"。修复前：
`FusionCenter` 的航迹只喂 AI 诊断与压力测试；RL 观测走
`sensor.fusion.fuse_measurements` 的**无状态航迹表**。两条链没有打通。

本层（`observation.py` + `tasks.py`）把融合输出翻译成调度器可只读消费的观测。

### 10.2 三条硬约束（由构造方式保证，不靠约定）

| 约束 | 实现方式 | 钉住它的测试 |
| --- | --- | --- |
| **调度器不持有真值 Simulator** | `observation.py` 的签名只接受 `FusionCenter` / `NodeState` / 已到达消息；模块的 **import 里没有** `engine.*` / `sensor` / `torch` | AST 扫 import（子串匹配会把文档字符串里的声明误判成违规） |
| **中央只读已到达的数据** | `CentralObservationStore.ingest()` 拒绝 `arrived_at is None` 或 `arrived_at > now`；`ingest_arrived()` 走 `CommBus.consume`（本身只交付已到达） | 延迟链路下逐条验证 + 绕过总线的二层防线 |
| **变长 + 有效掩码** | 航迹与节点都是列表 + 掩码；定长需求走**独立适配器** | 掩码/溢出/维度检查 |

### 10.3 字段元数据（单位 / 坐标系 / 可见范围 / 来源）

25 个字段全部登记在 `FIELD_SPECS`，未登记的字段会被 `assert_fields_documented` 拦下。
"可见范围"三档：

| visibility | 含义 | 例子 |
| --- | --- | --- |
| `local` | 只有本节点知道 | 自己的资源余量、本地航迹 |
| `shared` | **必须经通信到达**才可见 | 远端节点摘要（`arrived_at_s`） |
| `derived` | 由前两类推导 | `information_age_s`、`node_information_age_s`、`missing` |

坐标系一律 **ENU**（x=东, y=北, z=天）；速度 m/s；时间 s（相对仿真起点）；
资源量单位见 §1。每次观测导出都会带上完整的 `field_metadata()`，
所以"这个数是什么单位、哪个坐标系、谁能看见、从哪来"可以逐字段查。

### 10.4 观测内容

`TrackObservation`（每航迹）：稳定的 `track_id`、`position`/`velocity`、
`sigma_position`、`last_measurement_time_s`、`last_fusion_time_s`、
`information_age_s`、`coasting`（是否**预测保持**）、`n_sources`、
`source_sensor_ids`、`platforms`、`local_updates`/`remote_updates`。

`NodeObservation`（每节点）：上述航迹列表 + **有效掩码**、可用性、更新周期、
资源**容量与余量**、**已到达**消息数、在途消息数（**只报数量，不看内容**）、
缺失原因列表。

`CentralObservation`（中央）：节点列表 + 节点掩码 + 逐节点摘要年龄 + 缺失列表 +
`schema_version` + `legacy_observation_modes`。

### 10.5 中央观测的"冻结"语义（验收核心）

> **断开远端消息后，调度器不能继续"知道"远端的新信息。**

实现：中央只保存**最后一次到达**的摘要，`node_information_age_s = now − arrived_at`。
断开后：

* 该节点摘要内容**冻结**（不再更新）；
* 年龄**随全局时钟增长**；
* `missing` 里出现 `summary_age_<x>s`，缺失被显式标出而不是悄悄补齐；
* 从未收到过的节点 `node_valid_mask=False`、`missing=[summary_never_arrived]`，
  其航迹**完全不出现**在 `all_track_ids()` 里。

实测（`verify_v4.py` §16）：本地视图冻结在 `3239.20 m`，
而底层真值已到 `3480.0 m` —— 中央**没有**跟上。

### 10.6 通信载荷白名单按类型分开

观测摘要走 `MESSAGE_KIND_NODE_OBSERVATION`，它**有自己的白名单**：

* 固定字段（`node_id` / `observed_at_s` / `n_tracks` / 资源容量与余量 / 消息计数）；
* 逐航迹字段键形如 `track_<序号>_<字段>`，字段只能是登记过的那 17 个；
* `FORBIDDEN_PAYLOAD_PREFIXES`（`truth` / `err_` / `is_false_alarm`）
  对**测量与观测摘要一律生效**。

为什么不把观测字段塞进测量白名单：那会稀释测量的类型边界；
为什么不另开一条绕过白名单的通道：那会拆掉真值泄漏的最后一道闸门。
默认类型仍是 `measurement`，因此既有行为逐位不变。

### 10.7 任务队列（`tasks.py`）

四类任务：`predefined_sample`（预定义采样）、`estimate_update`（已有估计的更新）、
`process`（处理）、`share`（共享）。每个任务显式带
**释放时间 / 截止时间 / 预估成本 / 所属节点 / 完成状态**，
以及 `created_from` 溯源字段（记下"当时看得见哪些航迹、选中了哪些"）。

状态机：`pending → released → submitted → completed | rejected | expired | cancelled`。

**未知对象不得依据 `truth_id` 提前创建任务**——判据是**可见性**而不是模式匹配：

* `create_from_observation()` 是唯一的自动建任务入口，它只遍历观测的
  `track_ids()`（有效掩码为真者），调用方**没有**传任意对象键的入口；
* `enqueue_for_observation(targets=[...])` 会核对每个对象键是否在观测里，
  否则抛 `UnknownObjectError`——即便传入的是一个像真值 ID 的字符串
  （`TGT1`），只要调度器没看见过它，就会被拒；
* 航迹为空时**只**下发预定义采样；空观测建"更新任务"直接报错。

**看不见的目标不产生任务。**

### 10.8 定长适配器（`FixedLengthAdapter`）

旧 DQN 需要定长输入时用它，而**不能**"截取前几维"或"硬塞进旧维度"：

* 有自己的 `schema_version`（`rm-obs-1.0+fixed<slots>`）与 `output_dim`；
* `check_checkpoint_dim(dim)` 在维度不匹配时**直接报错**——
  实测拦下旧路径的 12 / 16 / 53 维；
* 编码布局与归一化尺度显式列出（`PER_SLOT_FIELDS` / `TAIL_FIELDS` / `SCALES`），
  没有魔法数；
* 超出槽位的**有效**航迹由 `overflow_count()` **显式报出**，
  而不是静默丢弃。

### 10.9 旧路径的处置

`full` / `pomdp` / `ideal` / `realistic` **全部保留、语义冻结**，
并在 `LEGACY_OBSERVATION_MODES` 里显式标记，同时出现在中央观测的序列化结果里。
本层使用独立的 `SCHEMA_VERSION = "rm-obs-1.0"`。
**旧 checkpoint 不得用于本层的输入**（维度检查会拒绝），
旧路径也不得混用本层字段。

| --- | --- |
| **断开远端（验收核心）** | 链路正常时中央能看到远端航迹推进；断开后视图冻结、不跟随真值、年龄增长、缺失显式标出 |
| `no_share` | 中央完全收不到远端摘要，`all_track_ids()` 为空 |
| 未到达消息 | 总线不交付在途消息；绕过总线直接递消息也被 store 拒绝（二层防线） |
| 航迹删除 | 删除后从观测消失，`missing` 出现 `no_track_local` |
| 空列表 | 结构有效、掩码为空、只产生预定义采样、不能建更新任务 |
| 节点数量变化 | 变长节点列表 + 掩码；后加入的节点在到达前一直是 `False` |
| 记录重放 | 同一序列重放得到**逐位相同**的观测与任务集 |
| 未知对象 | 三类真值样式键全部被拒；空队列不变 |
| 任务契约 | 释放/截止/成本/节点/状态/去重/`due`/`expire`/四类任务/转执行器请求 |
| 定长适配器 | 自有 schema、拒旧维度、掩码编码、溢出显式报出 |
| 字段与真值隔离 | 字段元数据完整；AST 证明不 import 真值层；序列化无真值通道；载荷白名单拦真值键 |
| 与真实 env 集成 | 用真实 `LpiPowerEnv` + `FusionCenter` 验证观测的航迹 ID 与位置**逐位来自融合输出** |

### 10.11 本层**没有**做的

* **没有把适配层接进 RL 训练/评测入口**：本层只提供只读观测与任务队列，
  没有替换 `full` / `pomdp` / `ideal` / `realistic` 任何一条路径，
  也没有训练任何新策略；
* **没有实现调度器本身**：任务队列会产出 `TaskRequest`，
  但"选哪个任务、什么时候提交"的策略尚未实现；
* **没有跨节点航迹关联**：中央看到的是各节点各自上报的航迹，
  不同节点的同一条真值航迹**不会**被合并成全局航迹 ID
  （这是下一阶段的事，且必须先解决信息边界问题）；
* **没有用真实 OOSM 语义**：观测摘要按"最后到达"覆盖，
  乱序到达的旧摘要会被更新的覆盖（时间戳只记录不改序）。

## 11. 非学习型调度闭环（v4.5：先把闭环跑通）

目标不是"性能"，而是**验收四件事**：

> 1. 三个基线共用同一份观测 / 同一个队列 / 同一个执行器；
> 2. 系统确实产生**不同分工**；
> 3. 每次分工都有**可读原因 + 结构化证据**；
> 4. 分工**真的被执行**（计划日志、账本、任务时间线三者对得上）。

外加一条纪律：**不预设任何策略必须更好**。规则调度在本场景里并没有提高
完成率，且存在真实局限（§11.6），都照实记录。

### 11.1 分层与唯一接触真值的地方

```
closed_loop.py（编排层，**唯一** import engine/sensor/fusion 的资源模块）
   ① 世界：Simulator + 场景推进 + 目标运动         ← 真值只在这里
   ② 各节点：自己的 FusionCenter ← 只吃本节点传感器的测量
   ③ 通信：CommBus ← 只传**节点观测摘要**，中央只能读已到达的
   ④ 调度：scheduler.plan() → 标准 ExecutionPlan
   ⑤ 执行：executor.submit() → 校验 + 记账（本层不直接写传感器/融合内部）
scheduling.py / observation.py / tasks.py：**不 import 真值层**（AST 扫 import 钉住）
```

`tests/test_resource_management.py` 的"不 import engine/torch"检查按**模块白名单**
精确化：`closed_loop.py` 是设计上必须依赖物理层的编排层，其余模块保持零依赖；
并且例外是**可证伪的**——若 `closed_loop.py` 哪天不再 import `engine`，测试会
要求把它移出白名单（防止豁免变成长期豁免）。

### 11.2 三个基线（差别**只在排序与选择**）

| 策略 | 依据 | 特点 |
| --- | --- | --- |
| `round_robin` | 节点轮流 + 节点内**先到先服务** | 最弱基线：不看紧迫性、不看新鲜度 |
| `edf` | 只看 `deadline_s` | 没有截止时间的排最后 |
| `rule` | 教学任务等级 + 等待时间 + 数据新鲜度 + 估计质量 | 四项**全部可观测**，逐项可算出来 |

`rule` 的打分（权重全部显式在 `SchedulingConfig` 里）：

```
priority = 0.3 × 任务等级
         + 0.5 × min(1, 等待 / starvation_threshold)
         + 0.6 × min(1, 信息年龄 / max_information_age)
         + 0.4 × min(1, 位置σ / max_sigma_position)
```

**没有**军事目标价值、威胁度、对抗效能之类的项；证据里也禁止出现这些字段
（测试逐键检查 `threat` / `target_value` / `kill` 等）。

### 11.3 排序键里**不能**放 deadline（一次真实回归）

轮询基线的排序键若把 `deadline_s` 当并列时的次级键，同一节点内的任务就会被
deadline 排成 EDF 的样子——实测两个基线在同一条任务上选出**相同**结果，
"轮询"名不副实。修法是排序只用 `(优先级, 释放时刻, 入队序)`，并加一条测试：
**把截止时间全部对调，轮询的分工不变**。

### 11.4 语义定义（用户点名要求）

| 语义 | 定义 | 关键性质 |
| --- | --- | --- |
| **完成** | 执行器 `applied` 且记账 | 计入分子 |
| **过期** | 截止时间到、任务失去意义 | **不删除**，仍计入分母 |
| **主动放弃** | 等待超 `abandon_after_s` 且仍无法服务 | 状态 `cancelled`，**仍留在队列**，分母不变 |
| **重复请求** | 同 `task_id` / 同去重键 / 计划内重复 | 拦下且**不重复扣费** |
| **长期未获服务** | 等待超阈值且**不是**因截止时间到期而离开队列 | 与"过期"**互斥** |

完成率分母 = 完成 + 过期 + 放弃 + 执行器拒绝 + 长期未获服务。
**主动放弃不会让分母变小，因此"删掉难任务"只会让完成率下降。**

"互斥"这一条是修出来的：第一版只在运行结束时统计"仍在排队且等待超阈值"的任务，
而默认场景里所有任务都带 2~6 s 截止余量、饿死阈值是 8 s，于是任务**总是先过期**，
`n_starved` 恒为 0——这条语义形同不存在。反过来若两个计数都记同一条任务，
完成率分母会被重复计入（偏低也是错）。现在由 `close_tick()` 统一定序，
并由定向用例 `test_starvation_and_expiry_are_mutually_exclusive` 钉住。

### 11.5 四种场景机制（全部用**已有**机制，不新增物理）

| 机制 | 实现 | 闭环里的可观测后果 |
| --- | --- | --- |
| **节点不可用** | `unavailable_windows` | 该节点在窗口内 `not_eligible`，另一节点照常承接 |
| **覆盖交接** | 两节点几何/朝向不同，目标从 A 视野进入 B 视野 | 逐节点**可见目标数**随时间变化 |
| **通信延迟** | `CommConfig.base_delay_s` | **内容年龄**上升；开头若干 tick 中央什么都收不到 |
| **观测偏差** | 某节点 `SensorConfig` 偏置字段 | 该节点航迹协方差变大 → 规则调度更该补它 |

**"内容年龄"是为这次修复新增的指标**：原来只记"到达年龄（now − 到达时刻）"，
而延迟 2 s 的摘要在**送达那一 tick 的到达年龄仍是 0**（"刚收到"），
于是"通信延迟"这条机制在指标上完全不可见（快/慢两个配置都记 0.000）——
这不是机制没生效，是**指标口径选错了**。现在同时记：
`node_information_age_s`（到达年龄）与 `node_content_age_s`（= now − 摘要生成时刻）。
调度器判"数据还新不新"应当看后者。

### 11.6 实测结果（`tools/compare_schedulers.py`，种子 42/7/13，24 tick）

| 场景 | 策略 | 完成 | 完成率 | 过期 | 截止违背 | 平均等待(s) | 通信(B) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| base | round_robin | 48 | 0.192 | 202 | 5 | 3.52 | 384 |
| base | edf | 48 | 0.195 | 198 | 38 | 5.58 | 640 |
| base | rule | 48 | 0.195 | 198 | 35 | 3.29 | 0 |
| node_outage | round_robin | 45 | 0.184 | 200 | 18 | 4.49 | 384 |
| node_outage | edf | 47 | 0.194 | 195 | 35 | 5.57 | 640 |
| node_outage | rule | 45 | 0.186 | 197 | 32 | 3.33 | 0 |

**四条必须一起读的诚实结论**：

1. **完成率由服务上限封顶，不是策略优劣**。本版本执行器只支持立即执行，
   所以每节点每 tick 最多落 1 个任务（`max_serviceable_tasks = 2 × 24 = 48`），
   而任务由可见航迹逐 tick 派生，实测**需求/能力 ≈ 6.3**
   （`service_capacity` 指标把它显式记下来）。完成量自然被 48 封顶，
   策略只改变**先做哪一件**。
2. **规则调度把某一类服务永久饿死**：`rule` 把 48 个名额**全部**给了等级最高的
   `estimate_update`，`share` 完成 0/42、`predefined_sample` 完成 0/34。
   原因是 `share` 不绑定航迹、没有信息年龄与协方差项，只有等级分，而同一 tick 内
   所有任务的等待时间相同，于是它永远排不到前面。这是**如实记录的设计局限**，
   要改变它需要给"从未被服务的服务类别"单独加项。
3. **EDF 的截止违背数最多**（38 vs 轮询 5）。这不是笔误：EDF 优先做"最紧急"的，
   而紧急任务往往正是预算最吃紧、最难按时做完的那些。
4. **种子影响是分场景的**：只有带链路抖动的 `constrained_comm` 逐种子有差异，
   `base` / `node_outage` / `bias` 逐种子**完全相同**（标准差全为 0）——
   检测被强制成功、虚警率为 0，噪声只影响量测精度、不改变"哪条航迹可见"。
   因此这三个场景的"3 个种子"**不构成统计重复**，报告里会显式警示。

**分工确实因策略而异**（`work_division_differs` 在四个场景全部为真）：
轮询/EDF 两类服务都做（A、B 两节点均承接 `estimate_update`/`predefined_sample`/`share`），
而规则只做 `estimate_update`。

### 11.7 两个被修掉的实现缺陷（都会静默给出错误结论）

| 缺陷 | 表现 | 修法 |
| --- | --- | --- |
| **闭环从未推进场景** | 目标全程静止，"沿 x=1500 向 +y 运动 → 依次进入 A/重叠区/B"的注释是**假的**，覆盖交接在结构上不可能发生（两节点每 tick 都看到同一目标，可见目标数恒为 1） | 每 tick 调 `sim.scene.advance_all(1.0)`（同时推进位置与时间戳，保持 Scene 的时间同步约束） |
| **每节点每 tick 限额 >1 会静默炸掉整份计划** | 执行器只支持立即执行，同一节点两段从当前时刻开始的占用必然重叠 → `PLAN_FATAL` 占用冲突 → **整份计划被拒**。实测限额设 2 时：计划数 96、完成数 **0**、通信 0 B，指标表上看起来像"策略变差了" | `SchedulingConfig.validate()` **直接拒绝** >1，并在报错里说明原因与正确做法（调预算或降低任务派生速率） |
| **等级权重让规则退化成严格优先级** | 等级差最大 3−1=2，另三项之和上限 0.5+0.6+0.4=1.5；`weight_level=1.0` 时等级**永远**压过服务需求，"等待时间"这一项形同不存在 | 改为 `0.3`（等级差 0.6 < 1.5），等级仍起作用但可被"已长期等待 + 数据已旧"翻越 |

**但要说清楚这次改动的真实效果**（逐项有测试，不是估计）：

* `weight_level=1.0` 时等级差 2.0 > 另三项之和上限 1.5 → **数学上不可能**翻越，
  规则就是严格优先级；
* 改成 `0.3` 后等级差 0.6 < 1.5，翻越**成为可能**：
  一条等级 1 但已等 10s、且绑定航迹又旧又差（年龄 6s、σ=300m）的任务
  确实能压过一条刚释放、航迹很新的等级 3 任务
  （`test_low_level_task_can_outrank_high_level_one`）；
* **但这没有解决 `share` 的饿死**：`share` 不绑定航迹 → 信息年龄与协方差项
  都是 `None` → 计 0，优先级上限只有 `0.3 + 0.5 = 0.8`，
  而一条"零需求"的等级 3 任务是 `3 × 0.3 = 0.9` —— **永远差 0.1 分**
  （`test_target_less_task_cannot_use_service_need_terms` 把这个上限钉住，
  将来若给这类任务补上服务需求项，那条测试会失败并提醒同步改文档）。

所以：权重改动本身正确（它让"长期等待可以翻越等级"这条语义**成立**），
但它**不是**饿死问题的修复。把"没有实测效果"说成"已修复"是本项目明确禁止的做法。

### 11.8 只读 AI 诊断桥（`ai_bridge.py`）

`explain_schedule(payload, remote_call, timeout_s)` 把逐条决策的理由与证据交给
可选的**远端**解释器；**远端超时不阻塞仿真时钟**：

* 用 `ThreadPoolExecutor` + `future.result(timeout)`，超时后走本地规则解释；
* 实测：2 s 的慢 provider + 0.3 s 预算 → **0.335 s** 返回，
  `explanation_timeout=True`、`provider="local_rule"`；
* 桥接层**不 import 时钟**（AST 扫 import 钉住），因此它没有任何推进时钟的路径；
* 桥接层不修改队列与决策（对照调用前后的序列化结果）。

### 11.11 本层**没有**做的

* **没有实现"提交什么任务"的策略**：任务仍由可见航迹逐 tick 派生
  （每目标每 tick 采样 + 更新 + 共享），因此需求约为服务上限的 6 倍。
  这是**任务派生速率**而非调度器的问题，属下一阶段；
* **没有给"从未被服务的服务类别"加项**：`rule` 因此会永久跳过 `share`
  （§11.6 第 2 条），如实记录未修；
* **没有做统计意义上的策略比较**：默认场景逐种子同值，需要先打开概率检测 /
  虚警或随机化场景，才能谈"重复实验"；
* **没有让 SHARE 任务产生可观测收益**：节点摘要在闭环里是**无条件发布**的，
  `share` 任务的成本照扣、收益为零，因此"规则调度跳过 share"在当前模型下是
  **理性的**。这是建模缺口（共享的收益链路尚未接进资源约束），不是调度器错误；
* **没有跨节点航迹关联 / 没有性能目标**（同 §9）。

## 12. 非学习优化参考与阶段冻结（大阶段一收尾）

### 12.1 先纠正一个概念：「有前瞻」≠「理论上界」

只有在一个**被完全枚举**的小问题上求出的解，才可以称"该问题的精确最优"。
滚动规划、束搜索、任何带启发式的推演，**只能**称"优化参考"。

这条纪律由代码结构保证（不靠自觉）：

* `exact=True` **只有一条**产生路径——组合全部枚举完 **且** 未触预算
  **且** 预测时域为 1；
* 声明文本必须**逐字**等于 `CANONICAL_CLAIMS` 的渲染结果（白名单），
  渲染参数一并存进结果供逐字比对；
* 结构化 `claim_kind` 必须与 `exact` 一致；
* `exact` 声明还必须"有据"：报出的组合总数 > 0 且展开次数 ≥ 该总数。

> 第一版自审用关键词扫描（"声明里是否出现『理论上界』"），结果**否定句**
> （"不是整个调度问题的理论上界"）被误判成"自称理论上界"。
> 关键词既会误报、也能被措辞绕过，因此改成白名单 + 结构化类型。

### 12.2 优化参考与规则基线**共用**什么

| 共用项 | 实现方式 |
| --- | --- |
| 任务定义 | 同一个 `TaskQueue` / `QueuedTask`（成本、截止、去重键） |
| 资源预算 | 观测里的 `capacity`/`remaining`（**只读**，不碰账本） |
| 信息权限 | 只读 `CentralObservation`；不 import 真值层（AST 钉住） |
| 执行器 | 输出同一个标准 `ExecutionPlan`，由 `UnifiedExecutor` 校验记账 |
| 候选语义 | 继承 `SchedulerBase._classify_due` 与 `_duplicate_rule` |
| 计时口径 | 都在 `SchedulerBase.plan` 里计时（**对称测量**，见 12.5） |

为此把 `SchedulerBase.plan` 重构成**模板方法**：候选筛选（不可服务 /
主动放弃）与重复判定统一在基类，`_select` 才是可替换的部分。
不共用这段逻辑的后果很具体：两条路径的"什么算放弃"迟早分叉，
那时对比的就不是"选择策略不同"，而是"问题定义不同"。

**不共用**的只有"挑哪一条"：规则基线用打分排序，优化参考用
"显式预测模型 + 声明式目标 + 有预算的搜索"。

### 12.3 不得读取未来的四类信息

| 禁止 | 保证方式 |
| --- | --- |
| 未来真实测量 | 预测只用当前可见观测外推 |
| 未来故障 | 模型里**没有**这条信息：`unavailable(t+k) = []` 是显式假设 |
| 隐藏对象状态 | 只能引用 `observation.track_ids()` 里的键 |
| 真值 | 优化层不 import `engine`/`sensor`/`fusion` |

静态扫描之外还有一条**运行时对照**（阶段验收第 3 项）：把 NODE_B 的未来
不可用窗口改掉、当前观测不变，**故障窗口之前的规划必须逐位相同**，
窗口之内允许不同（否则说明扰动没生效）。这是"没有偷看未来"的决定性证据。

7 条预测假设随结果一起落盘，其中两条是**已知的乐观假设**，报告里必须一并给出：
`persistent_tracks`（假设航迹在时域内始终可见）与
`arrival_rate`（未来到达数 = 当前观测到的到达数）。

### 12.4 六维评价向量（不给综合分）

完成度 / 及时性 / 估计质量 / 资源消耗 / 通信开销 / 计算耗时，
每项带单位、方向与逐字定义（见 §11 与 `docs/resource_contract_v1.md` §1.3）。

**预测向量与实测向量严格分开**：优化参考内部排序用的是**预测**向量
（`provenance="predicted"`），报告里的对照用的是**实测**向量
（`provenance="measured"`）。混在一起就会得出
"用预测的好处去比实测的代价"这种错误结论。

### 12.5 计算预算（防止无限推演）与**它带来的可复现性问题**

预算有四个维度：`max_expansions`（候选计划评估次数上限）、
`max_horizon_ticks`（预测时域上限）、`pareto_max_points`（**后处理**上限——
帕累托是非支配筛选、代价 O(n²)，实测 713 个向量要 0.022 s；
第一版预算只管搜索循环不管后处理，那是假预算）、
以及 `time_limit_s`（墙钟上限）。

**墙钟上限与"可复现"直接冲突**，这一点是被阶段验收逼出来的：

> 同一配置连跑四次，展开数分别是 **1315 / 1270 / 1312 / 1292**——
> 机器负载不同 → 停止点不同 → 计划也因此可能不同。
> `verify_v4` 第 18 节曾因此**偶发失败**（4/5），不是随机噪声，
> 而是一个真实的性质缺陷。

处置方式（不是把验收条件放松，而是把方法改成确定的）：

* `time_limit_s` 的角色降级为**安全阀**，默认 5 s（在本沙盒里不会触发）；
  确定性由 `max_expansions` 与 `max_horizon_ticks` 保证；
* 一旦安全阀真的触发，`deterministic` 置 False、`time_limit_triggered` 入账，
  **该次结果不允许被当作可复现基准**；
* 阶段验收第 5 项**显式要求**优化参考的搜索是确定性的
  （`non_deterministic_runs` 必须为空），而不只是"两次跑出来一样"。

超支仍然**如实记录**（`overrun_s`）：预算检查在每次展开**之前**做，
最后一次展开与后处理可能把总时长顶过上限。

### 12.6 实测结果（`evaluate_resource_management.py`，种子 42/7/13，24 tick）

三个种子在本配置下**逐位相同**（检测强制成功、虚警率 0，噪声不改变"哪条航迹可见"），
因此下表每个数字都是三次一致的取值，而不是均值。

| 场景 | 方法 | 完成度 | 及时性 | 估计质量 | 资源消耗 | 通信(B) | 计算耗时(s) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| base | rule | 0.1951 | 0.2708 | 0.4985 | 0.2538 | 0 | 0.019 |
| base | enumeration | 0.1920 | **1.0000** | 0.4985 | 0.2289 | 1024 | 0.174 |
| base | rolling_horizon | 0.1920 | **1.0000** | 0.4985 | 0.2251 | 1152 | 0.383 |
| node_outage | rule | 0.1860 | 0.2889 | 0.5386 | 0.2531 | 0 | 0.018 |
| node_outage | enumeration | 0.1829 | **1.0000** | 0.5386 | 0.2382 | 640 | 0.236 |
| node_outage | rolling_horizon | 0.1829 | **1.0000** | 0.5386 | 0.2334 | 896 | 0.642 |

**怎么读这张表**（五条一起读）：

1. 优化参考把**及时性从 0.27 提到 1.00**（48 条完成里 13 条按时 → 48 条全按时），
   代价是 **9~35 倍规划耗时**与约 1 KB 通信。这是**真实的取舍**，不是"谁更好"；
2. **规则基线在 24 次规划中有 6~11 次做到完全枚举**（`枚举` 列），
   其余次数因组合数超预算降级为束搜索——降级一律**不声明**精确最优；
3. **没有任何方法支配其他方法**（`base` 场景）：规则基线在通信为 0 与
   计算耗时上最优，优化参考在及时性上最优。这正是必须用向量而不用综合分
   的原因。`node_outage` 场景里枚举参考支配滚动规划参考——但那是**两者之间**
   的比较，不涉及规则基线；
4. **完成度几乎不变**（0.195 → 0.192）：因为完成度由**服务上限**封顶
   （需求/能力 ≈ 6.3），不是由调度决定的；
5. **`estimate_quality` 三个方法完全相同**：节点摘要每 tick 无条件发布，
   中央看到的新鲜度不由被调度任务决定。这是**建模缺口**，不是谁的功过。

> 把墙钟安全阀从"预算"降级为"兜底"之后，规划耗时**上升**了
> （rolling 0.24 s → 0.38 s）：之前的数字里有一部分是**安全阀截断搜索**
> 省下来的，不是方法真的更快。这也说明了为什么"耗时"必须和
> "预算触发次数"一起报告。

### 12.7 修掉的两个模型缺陷（都会让"优化参考"变成错的参考）

| 缺陷 | 症状 | 根因与修法 |
| --- | --- | --- |
| **期末效应** | 滚动规划在 24 个 tick 里只排 11 次、13 次**选择什么都不做** | `estimate_quality` 只在**时域末尾**取值 → "现在刷新"要让年龄再涨满整个时域才被测量，而"晚一个 tick 再刷新"在末端更新鲜 → 模型在**奖励拖延**。改为**时域内平均**，早刷新严格不差于晚刷新 |
| **完成度对选择不敏感** | 资源罚项一家独大，进一步推动"不干活" | 预测完成度的分母取了整个候选池（20+ 条），而每 tick 只能服务 2 条 → 无论选谁比值都≈2/25。改为只统计**截止时间落在预测时域内**的任务（这些任务在时域内要么被救下、要么作废，首 tick 的选择对它们有决定性） |

修掉之后：12/12 tick 都在干活，及时性达到 1.00。

**这两条都是"优化参考看起来更差"的缺陷，修它们不是为了让它好看**——
一个系统性选择"什么都不做"的参考方法根本不是参考。
修法本身有性质测试钉住（`test_estimate_quality_is_horizon_mean_not_terminal`、
`test_completion_scope_is_deadline_within_horizon`）。

### 12.8 精确性怎么验证：靠**独立暴力枚举**，不靠自证

`tests/test_resource_optimization.py` 自己枚举全部可行计划、自己求最大目标值，
再与优化器的选择比对。用优化器自己的搜索去"验证"优化器是自证，不算证据。
同时钉住：组合总数一致、评估数 = 总数、`exact` 标记正确、逐节点限额被遵守。

### 12.10 本层**没有**做的

* **没有跨 tick 的资源预留**：执行器仍只支持立即执行（`start_s == now`），
  因此每节点每 tick 最多 1 条；`reserved` 机制仍未被动用；
* **没有证明任何最优性之外的界**：滚动规划的 rollout 是声明式的，
  既不最优也没有近似比保证；
* **没有把共享/刷新的收益接进资源约束**：`share` 任务在当前模型里
  成本照扣、收益为零，因此 12.6 第 4 条那个缺口未修；
* **没有统计意义上的方法比较**：默认场景逐种子同值，需要先打开概率检测/
  虚警或随机化场景；
* **没有接学习算法**：本阶段到此为止（闸门见 12.9）。
