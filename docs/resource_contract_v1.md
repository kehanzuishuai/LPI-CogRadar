# resource-contract-v1：大阶段一冻结契约

> **状态：已冻结。** 版本 `resource-contract-v1`，
> 摘要见 `docs/resource_contract_v1.json` 的 `digest` 字段，
> 权威值同时写死在 `resource_management/contract_v1.py` 的 `FROZEN_DIGEST`。
> 任何一处口径改动都会让 `verify_frozen()` 失败。

## 0. 这份契约回答什么

大阶段一的交付**不是**"多了一个调度器文件"，而是：

> **资源管理问题已经定义清楚、并且能运行。**

要能说这句话，必须能回答"口径是什么、它有没有被动过"。
契约把口径做成**可校验摘要**，于是"动过"这件事会在导入即暴露，
而不是等有人对比两个数字时才发现。

## 1. 冻结内容（五块）

| 块 | 内容 | 校验入口 |
| --- | --- | --- |
| 观测 schema | 25 个字段的单位 / 坐标系 / 可见范围 / 来源 + `SCHEMA_VERSION = rm-obs-1.0` | `observation_schema_snapshot()` |
| 任务完成口径 | 7 种状态、完成率分母、饿死与过期的互斥定义、**不得删除任务** | `completion_semantics_snapshot()` |
| 资源模型 | 三类预算单位、教学成本模型、时长、守恒不变量 | `resource_model_snapshot()` |
| 基准配置 | 节点布局、逐节点预算、场景机制、调度默认值、固定种子与 tick 数 | `baseline_config_snapshot()` |
| 评价维度 | 6 维向量的逐字定义 + 声明式目标的默认权重 | `evaluation_snapshot()` |

### 1.1 完成口径（最容易被悄悄改动的一块）

完成率分母 = **完成 + 过期 + 主动放弃 + 执行器拒绝 + 长期未获服务**。

* 失败/放弃/过期的任务**一律不从队列里删除**——删掉难任务只会让完成率下降，
  不可能把它做高；
* **过期**：截止时间已过且未完成/未取消；
* **长期未获服务**：等待超过阈值，且**不是**因截止时间到期而离开队列
  （与"过期"**互斥**，否则完成率分母会被重复计入）；
* **主动放弃**：等待超过阈值且该节点仍无法服务；状态置 `cancelled`，
  任务**保留**在队列中。

### 1.2 资源不变量

对每个预算单位：`consumed + reserved + remaining == capacity`，三者均非负。
`occupancy_second` 是**时间占用量**，不是预算单位，不参与守恒式。

### 1.3 评价维度（6 维，逐字定义）

| 维度 | 单位 | 方向 | 定义 |
| --- | --- | --- | --- |
| 服务完成度 | 比值 | 越大越好 | 已完成 / (完成+过期+放弃+拒绝+饿死) |
| 任务及时性 | 比值 | 越大越好 | 截止前完成数 / 已完成数 |
| 估计质量 | 1/(1+秒) | 越大越好 | 实测取逐 tick 逐节点 `1/(1+平均信息年龄)` 的均值；预测取**时域内平均** |
| 资源消耗 | 容量占比 | 越小越好 | 三类单位 `consumed/capacity` 的算术平均（逐单位明细另附） |
| 通信开销 | 字节 | 越小越好 | 账本里的通信字节总量 |
| 计算耗时 | 秒 | 越小越好 | **规划**的墙钟时间总和（不含执行与仿真推进） |

**不给综合分。** 综合分只是搜索内部的声明式偏好（`ObjectiveSpec`），
换一组权重就换一个最优解，因此不能当作"方法好不好"的结论。

## 2. 冻结的纪律

### 2.1 "有前瞻"不等于"理论上界"

| 情形 | 允许的表述 | 禁止的表述 |
| --- | --- | --- |
| 单 tick 决策问题**完全枚举**完毕 | "该问题在该声明式目标下的**精确最优**" | "理论上界""全局最优" |
| 首 tick 枚举 + 后续声明式 rollout | "**优化参考**" | 任何最优性主张 |
| 组合数超预算 → 束搜索 | "**优化参考**（束搜索）" | 任何最优性主张 |
| 预算在枚举完成前耗尽 | "已评估部分中的最好解" | 任何最优性主张 |

这条纪律由代码结构保证，不靠自觉：

* `exact=True` **只有一条**产生路径——枚举组合数全部评估完 **且** 未触预算
  **且** 预测时域为 1；
* 声明文本必须**逐字**等于 `CANONICAL_CLAIMS` 的渲染结果（白名单，
  不是关键词扫描）；渲染参数一并存进结果，审计逐字比对；
* 另有结构化 `claim_kind` 必须与 `exact` 一致；
* `exact` 声明还必须"有据"：报告的组合总数 > 0 且展开次数 ≥ 该总数。

> 为什么不用关键词扫描：第一版用"声明里是否出现『理论上界』"判断，
> 结果**否定句**（"不是整个调度问题的理论上界"）被误判成"自称理论上界"。
> 关键词既会误报、也能被措辞绕过。

### 2.2 优化参考不得读取未来的四类信息

| 禁止 | 保证方式 |
| --- | --- |
| 未来真实测量 | 预测只能用当前可见观测外推（`PredictionModel`） |
| 未来故障 | 模型里**没有**这条信息：`unavailable(t+k) = []` 是一条显式假设 |
| 隐藏对象状态 | 只能引用 `observation.track_ids()` 里的键 |
| 真值 | 优化层不 import `engine`/`sensor`/`fusion`（AST 扫描钉住） |

除静态扫描外，还有一条**运行时对照**（阶段验收第 3 项）：
把 NODE_B 的未来不可用窗口改掉、当前观测不变，
**故障窗口之前的规划必须逐位相同**——窗口之内允许不同（否则说明扰动没生效）。
这是"没有偷看未来"的决定性证据，静态检查做不到。

### 2.3 预测假设必须随结果落盘

7 条假设全部随 `OptimizationOutcome.prediction` 一起保存，其中两条是
**已知的乐观假设**，报告里必须一并给出：

* `persistent_tracks`：假设当前可见航迹在时域内**始终可见**
  （真实覆盖交接会让航迹离开视野）；
* `arrival_rate`：未来每 tick 的新任务数 = 当前 tick 观测到的到达数。

### 2.4 预算是硬约束，但**墙钟预算会破坏可复现性**

`ComputeBudget` 的四个维度：

* `max_expansions`：候选计划评估次数上限（**确定性**，组合爆炸时能停下来）；
* `max_horizon_ticks`：预测时域上限（防"往前推 1000 步"式作弊，**确定性**）；
* `pareto_max_points`：**后处理**上限——帕累托是非支配筛选、代价 O(n²)，
  实测 713 个向量要 0.022 s。第一版预算只管搜索循环、不管后处理，
  那是个假预算；
* `time_limit_s`：墙钟上限，角色是**安全阀**，**不是**确定性预算。

**为什么墙钟只能是安全阀**：同一配置连跑四次，展开数分别是
1315 / 1270 / 1312 / 1292——机器负载不同 → 停止点不同 → 计划可能不同。
也就是说"以墙钟为预算"与"规则与优化参考可复现"这两条要求**直接冲突**。
处置方式是让方法变确定，而不是把验收条件放松：

* 默认 `time_limit_s = 5.0`，在本沙盒里不会触发；
* 一旦触发，`deterministic=False` 与 `time_limit_triggered` 如实入账，
  **该次结果不允许作为可复现基准**；
* 阶段验收第 5 项**显式要求** `non_deterministic_runs` 为空。

超支**如实记录**（`overrun_s`）：预算检查在每次展开**之前**做，
因此最后一次展开与后处理可能把总时长顶过上限。

## 3. 阶段验收清单（5 项）

未全部通过前**不进入学习算法阶段**；通过后也**不要求**规则方法必须失败、
学习方法必须胜出。

| # | 条件 | 判定方式 |
| --- | --- | --- |
| 1 | 多节点执行真实生效 | ≥2 个节点既有已规划任务、又在账本里有真实消耗；计划数 > 0 |
| 2 | 资源不超支 | 全部策略 × 种子 × 节点 × 单位的守恒残差为 0、`consumed ≤ capacity` |
| 3 | 信息不越权 | 运行时对照（改未来故障不改当前规划）+ 静态扫描 |
| 4 | 任务队列可追溯 | 逐状态计数之和 = 任务总数；每条决策/时间线行都带原因 |
| 5 | 规则与优化参考可复现 | 同配置重跑指纹逐位相同（**排除墙钟耗时**）；且冻结摘要一致 |

生成方式：

```bash
python evaluate_resource_management.py --acceptance
# → output/runs/<run_id>/resource_eval/acceptance/checklist.{json,md}
```

## 4. 冻结不等于不能改

改了会失败，不是不能改。正确流程：

1. 确认改动是必要的（不是"顺手"）；
2. 升 `CONTRACT_VERSION`；
3. 重算并写回 `FROZEN_DIGEST`
   （`python evaluate_resource_management.py --freeze` 会打印当前摘要）；
4. 同步 `docs/resource_contract_v1.json` 与本文件；
5. 重跑基线与阶段验收。

**禁止的是悄悄改。** 一旦口径悄悄漂移，"规则基线 vs 优化参考"的对比
就变成了"两套问题定义的对比"——那不是结论，是误会。

## 5. 已知局限（随契约一起冻结，不得在报告里隐去）

1. **完成度由服务上限封顶**：执行器只支持立即执行，每节点每 tick 最多 1 条；
   任务由可见航迹逐 tick 派生，实测需求/能力约 6 倍。
   完成度差异很小，**不能**单独用来判定方法优劣。
2. **`estimate_quality` 对调度不敏感**：节点摘要每 tick **无条件**发布，
   中央看到的航迹新鲜度不由被调度任务决定——实测三个方法该维度数值完全相同。
   这是建模缺口（共享/刷新的收益链路尚未接进资源约束），
   不是调度器的成绩或过错。
3. **优化参考的排名依据是预测向量**，报告里的向量是实测向量；
   预测模型含乐观假设，预测目标值高**不代表**实测更好。
4. **规则调度会把某一类服务永久饿死**：`share` 不绑定航迹 → 拿不到
   信息年龄/协方差项 → 优先级上限 `0.3+0.5=0.8`，低于"零需求"高等级任务的
   `0.9`。如实记录，未修。
5. **种子影响是分场景的**：默认场景里只有带链路抖动的场景逐种子有差异，
   其余逐种子完全同值，因此"3 个种子"不构成统计重复。
